## 1. 현황 요약

React와 FastAPI를 연결한 **규칙 기반 개발 버전**이다. 문자·URL 입력, 위험 표현 추출, 근거와 행동 안내, 스크린샷 OCR과 사용자 확인까지 동작한다. T5에서 TF-IDF 기준선 모델을 규칙과 함께 서버에서 실행하는 흐름을 붙였다(모델 파일을 준 경우만).

- 피싱 분류용 경량 AI는 **TF-IDF 문자 n-gram + 로지스틱 회귀 기준선 하나**만 연결했다(T5, 임시 정책, `docs/MODEL_POLICY.md`). 모델은 규칙의 정보 부족을 의심으로 올릴 수만 있다. 모델 파일은 저장소 밖에 두고 `PTOS_MODEL_PATH`로 주며, 없으면 규칙 결과만 낸다. LLM은 **미구현**이다. OCR의 인식 모델과 제품의 피싱 판정은 별개다.
- Google Safe Browsing v5 hashes.search의 실제 HTTP 전송기를 T6(2026-10-28)에서 연결했다. **기본은 꺼짐**이고 키와 `PTOS_SAFE_BROWSING_MODE=live-noncommercial`이 모두 있을 때만 조회한다. 실제 호출은 수동 확인 스크립트로 사용자가 직접 실행해 테스트 URL 1건의 위협 일치를 확인했고(`docs/SAFE_BROWSING_VALIDATION.md`), 자동 테스트는 가짜 응답만 쓴다. 탐지 범위는 측정하지 않았다.
- **실제 피싱 탐지 정확도 검증은 한 번도 없다.** 기존 테스트 통과는 코드 동작 검증이지 탐지 성능 검증이 아니다.
- 결과 계약은 4종(`normal`, `suspicious`, `dangerous`, `insufficient_information`)이지만 현재 `normal`은 반환하지 않는다. 그래서 정상 문자도 정보 부족으로 나온다.

## 2. 일정 위험

설계서 일정은 W8에 경량 모델과 조건부 LLM, W9에 1차 릴리즈다. 경량 모델은 TF-IDF 기준선만 연결했고(T5) LLM은 없다. 평가 수치는 소규모 파일럿뿐이므로, **중간발표에 보여줄 수치를 만드는 것**이 가장 급하다. 중간점검 시연은 규칙 + TF-IDF 기준선이 서버에서 함께 도는 흐름이며 성능 주장이 아니다. 현재 주차는 팀이 확인해 아래 로드맵에 날짜를 넣는다.

## 4. 평가셋 스키마 (제안)

원천 데이터의 이진 라벨을 4단계로 자동 변환하지 않는다. 4단계 라벨은 검수 지침에 따라 직접 부여한다.

| 컬럼 | 설명 |
| --- | --- |
| `id` | 고유 번호 |
| `text`, `url` | 입력 문자와 직접 입력 URL (없으면 비움) |
| `expected_level` | `normal` / `suspicious` / `dangerous` / `insufficient_information` |
| `label_reason` | 판정 근거와 경계 사례 여부 |
| `source`, `is_synthetic` | 출처와 실제·합성 여부 |
| `campaign_id` | 같은 캠페인·변형 문장·동일 도메인을 묶어 분할하기 위한 값 |
| `split` | `dev` / `test` (최종 테스트셋은 정책·임계값 조정에 쓰지 않음) |
| `review_status` | 검수자 간 합의 상태 |

- 정상 문자는 금융 안내, 택배, 인증, 광고를 나누어 포함하고, 정보 부족 사례와 OCR 오류·근거 충돌 사례도 별도로 넣는다.
- 현재 `normal`이 반환되지 않으므로, 하네스는 `normal` 기대 사례의 결과를 별도로 표시한다.
- 원본 데이터셋은 저장소에 커밋하지 않는다. 공개 가능한 최소 샘플과 스키마만 둔다.
- 하네스 사용법, `text`/`url` 중 하나만 채우는 규칙, 저장 위치와 개인정보 가리기는 `docs/EVALUATION.md`를 본다.

| OCR 포함 분석 | 10초 | OCR 엔진 15초, 브라우저 25초 | PRD 목표와 불일치. Tesseract를 실측하고 OCR 교체 또는 목표 조정 중 선택한다. |

- 측정은 요청 전송부터 결과 수신까지이며, 이미지 경로의 사용자 확인 시간은 제외한다. 환경·입력 길이·동시 요청 수를 고정하고 p50, p95, 시간 초과 비율을 보고한다.
- 측정은 Windows 개발 환경과 배포 환경(Linux)에서 각각 한다. Windows는 `--reload`·`--workers`를 쓸 수 없어 결과가 다를 수 있다.
- 경량 모델은 서버 시작 시 한 번 로드하고, CPU 추론 지연과 메모리를 먼저 잰다(`backend/measure_model.py`, 9절 기록). 모델 추론 제한은 1초(개발 제안)이며 넘으면 규칙 결과만 낸다. 트랜스포머 후보가 배포 사양에 맞지 않으면 기준선 모델이나 더 가벼운 모델로 간다 (결정 기준은 T5c에서 정한다).
- 합격선(p95 등)은 팀이 T1에서 정한다. 이 문서는 값을 제안하지 않는다.

## 6. 데이터와 이용 조건

## 7. 규칙 정책의 한계

규칙은 PRD를 바탕으로 프로젝트에서 작성한 개발용 정책이며 검증된 분류 규칙이 아니다. NIST Phish Scale은 단서 설명의 참고 자료일 뿐 현재 자동 판정 임계값의 근거가 아니다. 우회 표현, 부정, 인용은 놓치거나 오탐할 수 있고 실제 사칭 여부를 검증하지 않는다. 신호 6개(`FactorCode`): 기관·지인 명의 주장, 금전 요구, 인증번호·개인정보 요구, 링크 접속 요구, 앱 설치·실행 요구, 긴급성·불이익 압박. T4에서 계약을 바꾸지 않고 `rule_id`로 세부 신호(머리말, 가족 호칭, 확인 계열 링크, 불이익, 임박 기한)를 나눴다.

**모델 종합(임시, 팀 확정 필요, 정책 `rules-model-dev-v1`, API 응답 `analysis_version: rules-model-dev-v3`)**: 규칙 결과가 정보 부족이고 모델 점수가 임시 임계값 이상이면 의심(`MODEL_SIGNAL_ONLY`)으로 올린다. 의심·위험은 유지하고 내리지 않는다. 모델 신호는 원문 구절 근거가 아니어서 `evidence`에 넣지 않는다. 임계값 기준(dev OOF에서 normal 신호 0건을 지키며 사기 재현율 최대)도 임시이며 팀 확정이 필요하다. 상세는 `docs/MODEL_POLICY.md`.

**알려진 한계 (중간점검 이후 B안 검토)**: 모델이 함께 돌아도 응답 `analysis_mode`는 계약상 `"rules"`로 남고, 모델 단계의 로드 실패·시간 초과·오류는 모두 `unavailable`이며 limitations 문장으로만 구분된다. B안은 `analysis_mode: "rules+model"`과 단계 상태 `timeout`·`load_failed`를 추가하는 계약 변경이다.

**현재 판정 정책(임시, 팀 확정 필요, `rules-dev-v4`)**: 같은 문맥 안의 ① 명시적 명의 + 금전/민감정보/앱, ② 금전 + 민감정보/앱, ③ 긴급성·불이익 + 민감정보 + 링크, ④ (규칙 A) 명의(머리말 포함) + 불이익 + 링크 요구 + 임박 기한, ⑤ (규칙 B) 가족 호칭 + 금전 + 링크 요구 → 위험. 그 밖의 구체적 요구 → 의심, 나머지 → 정보 부족. `normal`은 반환하지 않고 `confidence`는 `null`이다. 머리말·가족 호칭은 단독으로 판정을 올리지 않는다. 임박 기한은 당일·금일·오늘·내일·익일 + 기한 표현, 자정까지, 24시간 이내, 1일 남음까지이며 2일 이상 남은 기한과 날짜만 적힌 기한은 해석하지 않는다. 답장 유도 신호는 미구현이다. v4: 관계 자기소개(“딸인데” 등)는 구절 첫머리일 때만 명시적 명의, 명의·긴급·불이익의 부정은 첫 연결 어미까지, 청구어 뒤 “없습니다/아닙니다”는 불이익 근거 아님, 업종 없는 머리말은 명의 아님. v4 2차: 민감정보·송금 요구 활용형(입력바랍니다·연결형·조건형·필요형), 앱 설치 필요형은 원격 지원·제어·APK일 때만, 번호를 보여 주고 공유 금지를 경고하는 정상 인증번호 안내는 입력 요구 근거에서 제외. 결제·납부형(B-2)과 요구문 뒤 주소(D)는 보류. 상세와 한계는 `docs/RULE_POLICY.md`를 본다.

- **dev 수치(사기 경고 203/258)와 차이가 크다.** 변경기록 기준으로 dev의 실제 문자 43건은 모두 정상이고, test에는 실제 사기 문자가 28건 있다. 규칙은 dev에서 놓친 문자를 보고 다듬었고 모델도 실제 사기 문자를 학습하지 못했다. 안전 쪽 지표(사기 → 정상 0, 정상 → 위험 0)는 test에서도 지켜졌다.
- **test는 이제 한 번 본 상태다.** test 행은 열어 보지 않았고 규칙·모델·임계값 조정에 쓰지 않았다. 이후 모델을 바꿔 같은 test로 다시 재면 그 수치는 한 번만 본 수치가 아니다. 최종 수치는 새 시험지(test-2)로 재는 것이 좋다.

**출처를 통째로 뺀 dev 재검증(임시 스크립트, 모델 파일 없음, dev만):** 기존 교차검증은 `campaign_id`로만 묶어 같은 출처의 비슷한 문장이 학습과 채점에 함께 들어갔다. dev 학습 대상 499행을 출처 4묶음(LGAI 192, KR-MOB 103, 직접 작성 177, 기타 27)으로 나눠 한 묶음을 빼고 학습한 뒤 그 묶음을 채점했다. 아래는 **모델 단독** 수치이고, 모아 놓은 점수에서 정상 오탐을 4건(2%) 이하로 두는 기준으로 사기 258건 중 신호가 난 건수다. 기준을 dev 점수에서 골랐으므로 이 수치도 낙관적이지만 기존 교차검증 수치보다는 덜하다.

- 정상 오탐 0건 기준에서는 더 낮다(같은 순서로 TF-IDF 36/76/36, 고정 e5 8/3/3, 미세조정 e5 2/13: 두 번째 구성이 13). 즉 현재 임계값 기준(“OOF 정상 오탐 0건”)은 처음 보는 유형에서 모델 신호를 거의 내지 못한다.

- 미세조정(e5 전체 가중치, 학습률 3e-5, 배치 16)은 CPU에서 한 스텝 약 7초라 입력 길이 128·2 epoch으로 줄여 실행했다. TF-IDF·고정 e5는 길이 256 기준이라 조건이 완전히 같지 않다. 미세조정은 소량 구성에서 고정 e5보다 나았지만(32 → 54) TF-IDF(88)보다 낮았다. **class 2 사기 600행을 더한 두 번째 구성에서는 105/258로 세 모델 중 가장 높았다**(빼 둔 LGAI 사기 68/100, KR-MOB 24/99, 직접 작성 13/59, AUC 0.869, 정상 임계값 미만 정상 89/241). 같은 구성에서 고정 e5는 22, TF-IDF는 51이었다. 한 번 실행한 결과이고 시드·epoch·입력 길이 변화에 대한 안정성은 보지 않았다. 학습에 쓴 LGAI와 같은 출처를 빼서 채점한 수치라 LGAI 사기에서 특히 높다(68/100). 그 밖의 출처(KR-MOB 24/99, 직접 작성 13/59)는 낮아 일반화가 충분하다고 보기 어렵다. **미세조정 모델은 서버에 적용하지 않았다.**
- class 2 사기 문자를 많이 넣어도 좋아지지 않았다. 정상 학습 자료(class 3)가 택배 안내뿐이고 틀이 적어 균형이 깨지는 것으로 보인다(확인한 사실이 아니라 해석이다).

**LGAI 원본 분류별 통계(`lgaidataset.csv` 19,009행, 본문은 출력하지 않음):** class 1 5,778행(앞 12글자 틀 5,775종, 길이 중앙값 23자, 링크·광고·인증번호 표현 0%), class 2 10,531행(틀 4,632종, 중앙값 53자), class 3 2,700행(틀 36종, 중앙값 155자, 전부 배송·택배 표현). **class 1이 무엇인지는 확인하지 못했다.** 정상 일상 문자라면 정상 학습 자료의 다양성 부족을 줄일 수 있다. 원본에는 평가셋(test 포함) 행이 들어 있으므로 학습에 쓰려면 평가셋과 겹치는 행을 뺀 정리본이 필요하다.

**규칙이 dev에서 놓친 사기 55건(부풀려진 수치의 나머지):** 주소가 있는 문자 36건, 입력 상태가 조각(`fragment`)인 문자 34건, 신호가 하나도 없는 문자 28건. 출처별로 LGAI 사기 41/100, KR-MOB 11/99, 직접 작성 3/59를 놓쳤다. “짧은 글 + 주소” 형태에 약하다.

- (T0에서 해결) Python 3.13 호환: OpenAPI 오류 응답 설명을 커밋된 문구로 고정했다 (3.13에서 422·413 기본 문구가 바뀜). Windows 호환: 긴 테스트 ID에 짧은 `ids`를 붙이고, Playwright가 Windows venv 경로로 백엔드를 시작하게 했다.
- 기타 문서(`docs/OCR_VALIDATION.md`, `docs/SAFE_BROWSING_VALIDATION.md` 등)의 "이번 PR·이번 증분" 같은 작성 시점 표현은 기록 문서라 그대로 두었다.
- 현재 개발 제한(JPG/PNG 한 장, 10 MiB, 2,000만 화소, OCR 엔진 15초, 브라우저 25초)은 제품 목표(문자 5초, OCR 10초)의 달성을 뜻하지 않는다.
- 이미지는 FastAPI 서버에서 처리하므로 클라우드 실행 시 해당 서버로 업로드된다.
- 메모리 캐시와 호출 예산이 여러 프로세스에서 분리되는 문제는 단일 프로세스 MVP로 보류하는 것을 T1에서 결정하고, 다중 프로세스 전환 시 재설계한다.
- **(중간점검 이후 검토, 계약 변경)** `Evidence`에 공급자(`provider`) 필드를 넣을지 검토한다. 지금은 `source: url_reputation`과 `urls[].reputation.provider`·출현 좌표를 맞춰 Google 근거를 구분한다. 또 `explanation`이 규칙 문장과 URL 문장을 이어 붙인 문자열이라 Google 표기를 설명문에는 붙이지 못하고 URL 결과·근거 옆에만 붙인다.
- 결과 제목 "위험"은 규칙과 평판을 합친 앱의 판정이다. Google 근거가 있을 때 Google의 단정적 판정처럼 읽히는지 고령자 사용성 검토(T8)에서 확인한다.

## 11. 다음 작업 순서

1. 복원한 소스에서 실행 환경과 테스트를 재확인한다. 실행·테스트 명령은 `DEVELOPMENT.md`를 따른다.
2. 라벨링 파일의 4단계 정답과 근거를 사람이 검수하고, 같은 캠페인이 양쪽에 섞이지 않도록 dev/test를 나눈다.
3. 평가 하네스로 현재 규칙의 기준선을 측정한다. 합성 데이터 결과와 실제 문자 결과를 구분하며, 위험 → 정보 부족과 위험 → 정상·의심을 따로 보고한다.
4. 기준선 확인 후 규칙 보강, 경량 모델(중간점검은 TF-IDF 기준선, 트랜스포머 비교는 이후)을 진행한다. URL 평판은 연결을 마쳤고(T6, 기본 꺼짐), 한국 스미싱 URL 탐지 범위 측정과 할당량 항목 확인이 남았다.
5. 근거 종합 정책과 조건부 LLM 기준을 검증하고, 단계별 지연·호출률·비용을 측정한다.
