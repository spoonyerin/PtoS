## 1. 현황 요약

React와 FastAPI를 연결한 **규칙 기반 개발 버전**이다. 문자·URL 입력, 위험 표현 추출, 근거와 행동 안내, 스크린샷 OCR과 사용자 확인까지 동작한다. T5에서 TF-IDF 기준선 모델을 규칙과 함께 서버에서 실행하는 흐름을 붙였다(모델 파일을 준 경우만).

- 피싱 분류용 경량 AI는 **TF-IDF 문자 n-gram + 로지스틱 회귀 기준선 하나**만 연결했다(T5, 임시 정책, `docs/MODEL_POLICY.md`). 모델은 규칙의 정보 부족을 의심으로 올릴 수만 있다. 모델 파일은 저장소 밖에 두고 `PTOS_MODEL_PATH`로 주며, 없으면 규칙 결과만 낸다. LLM은 **미구현**이다. OCR의 인식 모델과 제품의 피싱 판정은 별개다.
- Google Safe Browsing v5 hashes.search의 실제 HTTP 전송기를 T6(2026-10-28)에서 연결했다. **기본은 꺼짐**이고 키와 `PTOS_SAFE_BROWSING_MODE=live-noncommercial`이 모두 있을 때만 조회한다. 실제 호출은 수동 확인 스크립트로 사용자가 직접 실행해 테스트 URL 1건의 위협 일치를 확인했고(`docs/SAFE_BROWSING_VALIDATION.md`), 자동 테스트는 가짜 응답만 쓴다. 탐지 범위는 측정하지 않았다.
- **실제 피싱 탐지 정확도 검증은 한 번도 없다.** 기존 테스트 통과는 코드 동작 검증이지 탐지 성능 검증이 아니다.
- 결과 계약은 4종(`normal`, `suspicious`, `dangerous`, `insufficient_information`)이지만 현재 `normal`은 반환하지 않는다. 그래서 정상 문자도 정보 부족으로 나온다.

| 영역 | 구현됨 | 남은 것 |
| --- | --- | --- |

## 2. 일정 위험

설계서 일정은 W8에 경량 모델과 조건부 LLM, W9에 1차 릴리즈다. 경량 모델은 TF-IDF 기준선만 연결했고(T5) LLM은 없다. 평가 수치는 소규모 파일럿뿐이므로, **중간발표에 보여줄 수치를 만드는 것**이 가장 급하다. 중간점검 시연은 규칙 + TF-IDF 기준선이 서버에서 함께 도는 흐름이며 성능 주장이 아니다. 현재 주차는 팀이 확인해 아래 로드맵에 날짜를 넣는다.

## 4. 평가셋 스키마 (제안)

원천 데이터의 이진 라벨을 4단계로 자동 변환하지 않는다. 4단계 라벨은 검수 지침에 따라 직접 부여한다.

| 컬럼 | 설명 |
| --- | --- |
| `id` | 고유 번호 |
| `text`, `url` | 입력 문자와 직접 입력 URL (없으면 비움) |
| `expected_level` | `normal` / `suspicious` / `dangerous` / `insufficient_information` |
| `label_reason` | 판정 근거와 경계 사례 여부 |
| `source`, `is_synthetic` | 출처와 실제·합성 여부 |
| `campaign_id` | 같은 캠페인·변형 문장·동일 도메인을 묶어 분할하기 위한 값 |
| `split` | `dev` / `test` (최종 테스트셋은 정책·임계값 조정에 쓰지 않음) |
| `review_status` | 검수자 간 합의 상태 |

- 정상 문자는 금융 안내, 택배, 인증, 광고를 나누어 포함하고, 정보 부족 사례와 OCR 오류·근거 충돌 사례도 별도로 넣는다.
- 현재 `normal`이 반환되지 않으므로, 하네스는 `normal` 기대 사례의 결과를 별도로 표시한다.
- 원본 데이터셋은 저장소에 커밋하지 않는다. 공개 가능한 최소 샘플과 스키마만 둔다.
- 하네스 사용법, `text`/`url` 중 하나만 채우는 규칙, 저장 위치와 개인정보 가리기는 `docs/EVALUATION.md`를 본다.

## 5. 시간 예산 (제안, 측정 필요)

| 경로 | PRD 목표 | 현재 개발 제한 | 상태 |
| --- | --- | --- | --- |
| 텍스트 분석 | 일반 요청 5초 | 서버 5초, 브라우저 10초 | 측정 전 |
| OCR 포함 분석 | 10초 | OCR 엔진 15초, 브라우저 25초 | PRD 목표와 불일치. Tesseract를 실측하고 OCR 교체 또는 목표 조정 중 선택한다. |
| 조건부 LLM 경로 | 별도 측정 | 미정 | LLM 연결 시 서버·브라우저 제한을 재설계한다. |

- 측정은 요청 전송부터 결과 수신까지이며, 이미지 경로의 사용자 확인 시간은 제외한다. 환경·입력 길이·동시 요청 수를 고정하고 p50, p95, 시간 초과 비율을 보고한다.
- 측정은 Windows 개발 환경과 배포 환경(Linux)에서 각각 한다. Windows는 `--reload`·`--workers`를 쓸 수 없어 결과가 다를 수 있다.
- 경량 모델은 서버 시작 시 한 번 로드하고, CPU 추론 지연과 메모리를 먼저 잰다(`backend/measure_model.py`, 9절 기록). 모델 추론 제한은 1초(개발 제안)이며 넘으면 규칙 결과만 낸다. 트랜스포머 후보가 배포 사양에 맞지 않으면 기준선 모델이나 더 가벼운 모델로 간다 (결정 기준은 T5c에서 정한다).
- 합격선(p95 등)은 팀이 T1에서 정한다. 이 문서는 값을 제안하지 않는다.

## 6. 데이터와 이용 조건

## 7. 규칙 정책의 한계

규칙은 PRD를 바탕으로 프로젝트에서 작성한 개발용 정책이며 검증된 분류 규칙이 아니다. NIST Phish Scale은 단서 설명의 참고 자료일 뿐 현재 자동 판정 임계값의 근거가 아니다. 우회 표현, 부정, 인용은 놓치거나 오탐할 수 있고 실제 사칭 여부를 검증하지 않는다. 신호 6개(`FactorCode`): 기관·지인 명의 주장, 금전 요구, 인증번호·개인정보 요구, 링크 접속 요구, 앱 설치·실행 요구, 긴급성·불이익 압박. T4에서 계약을 바꾸지 않고 `rule_id`로 세부 신호(머리말, 가족 호칭, 확인 계열 링크, 불이익, 임박 기한)를 나눴다.

**모델 종합(임시, 팀 확정 필요, `rules-model-dev-v1`)**: 규칙 결과가 정보 부족이고 모델 점수가 임시 임계값 이상이면 의심(`MODEL_SIGNAL_ONLY`)으로 올린다. 의심·위험은 유지하고 내리지 않는다. 모델 신호는 원문 구절 근거가 아니어서 `evidence`에 넣지 않는다. 임계값 기준(dev OOF에서 normal 신호 0건을 지키며 사기 재현율 최대)도 임시이며 팀 확정이 필요하다. 상세는 `docs/MODEL_POLICY.md`.

**알려진 한계 (중간점검 이후 B안 검토)**: 모델이 함께 돌아도 응답 `analysis_mode`는 계약상 `"rules"`로 남고, 모델 단계의 로드 실패·시간 초과·오류는 모두 `unavailable`이며 limitations 문장으로만 구분된다. B안은 `analysis_mode: "rules+model"`과 단계 상태 `timeout`·`load_failed`를 추가하는 계약 변경이다.

**현재 판정 정책(임시, 팀 확정 필요, `rules-dev-v3`)**: 같은 문맥 안의 ① 명시적 명의 + 금전/민감정보/앱, ② 금전 + 민감정보/앱, ③ 긴급성·불이익 + 민감정보 + 링크, ④ (규칙 A) 명의(머리말 포함) + 불이익 + 링크 요구 + 임박 기한, ⑤ (규칙 B) 가족 호칭 + 금전 + 링크 요구 → 위험. 그 밖의 구체적 요구 → 의심, 나머지 → 정보 부족. `normal`은 반환하지 않고 `confidence`는 `null`이다. 머리말·가족 호칭은 단독으로 판정을 올리지 않는다. 임박 기한은 당일·금일·오늘·내일·익일 + 기한 표현, 자정까지, 24시간 이내, 1일 남음까지이며 2일 이상 남은 기한과 날짜만 적힌 기한은 해석하지 않는다. 답장 유도 신호는 미구현이다. 상세와 한계는 `docs/RULE_POLICY.md`를 본다.

### T4 규칙 보강 1차 비교 (2026-10-27)

T3과 같은 평가 CSV(SHA-256 `e65dd42f…49ea4`)로 비교했다. 보강 전 수치는 T3 기준선 리포트를 그대로 썼다. 보강 후는 커밋 `92b72d2` + 커밋되지 않은 T4 변경(`rules-reputation-dev-v2`)이다. **개발 중에는 `--split dev`만 반복했고, test는 코드를 확정한 뒤 마지막에 한 번만 실행해 전후 비교에만 썼다. test는 같은 1인 라벨링·합성 중심이며 기준선 때도 실행한 분할이라 독립 검증이 아니다.** 아래 수치는 탐지 성능 주장이 아니다.
