# 조건부 추가 검토(LLM) 단계 · llm-review-dev-v1

> **임시, 팀 확정 필요. 앱에 연결하지 않았다.** 어댑터, 가리기, 호출 조건, 종합 정책과 가짜 응답 테스트까지만 있다. `create_app`은 이 단계를 만들지 않으므로 환경 변수를 넣어도 실제 서버는 외부 LLM을 호출하지 않는다. 실제 외부 LLM 호출은 한 번도 하지 않았고 탐지 효과도 측정하지 않았다.

PRD FR-04~05의 "근거가 충돌하거나 불확실할 때만 조건부 LLM 호출"을 위한 구조다 (로드맵 T7).

## 왜 앱에 연결하지 않았나

사용자 본문(가린 것이라도)을 외부로 보내려면 다음이 먼저 필요하고, 모두 API 계약 변경이라 별도 브랜치에서 한다.

| 바꿀 곳 | 내용 | 이유 |
| --- | --- | --- |
| `ReadyResponse` | `llm_review: "live" \| "off"` 필드 | 화면이 "가린 문장이 외부 서비스로 전송될 수 있어요" 고지를 켜진 경우에만 보여 주려면 필요하다 (Safe Browsing의 `url_reputation`과 같은 방식) |
| `AnalysisStage.name` | `"llm_review"` 추가 | 단계의 수행·실패를 `analysis_stages`로 알리려면 필요하다. 지금은 `limitations` 문장으로만 알린다 |
| `AnalysisStage.status` (선택) | `timeout` 등 | 모델 단계의 B안과 같은 묶음 |

계약 브랜치에서 할 일: 위 필드, `create_app`에서 `create_llm_reviewer(os.environ)` 연결, 입력 화면 고지, OpenAPI·생성 타입·프론트 테스트·Playwright.

## 구조

- 경계: `LlmReviewer.review(masked_text) -> LlmReview` (`backend/app/llm_review.py`). 예외를 던지지 않고 상태로 알린다: `completed`, `timeout`, `unavailable`, `auth_error`, `rate_limited`, `invalid_response`, `budget_exhausted`.
- 전송기 `ChatCompletionsReviewer`: chat completions 형식(`POST {base_url}/chat/completions`, Bearer 키)이다. 공급자를 코드에 고정하지 않았다. 이 형식을 받는 공급자면 주소와 모델 이름만 바꿔 쓴다. **공급자·모델 선택과 이용 조건(입력 보관·학습 사용 여부, 국외 전송) 확인은 사람이 한다.**
- `CompositeAnalyzer(..., llm=None)`: 기본은 없음이다. 넣으면 규칙과 모델을 모두 본 뒤 조건에 맞을 때만 호출한다. 넣지 않으면 결과가 이전과 완전히 같다.

## 켜는 조건 (`create_llm_reviewer`)

백엔드 환경 변수가 **모두** 있을 때만 전송기를 만든다. `VITE_` 변수에 넣지 않는다.

| 변수 | 값 |
| --- | --- |
| `PTOS_LLM_API_KEY` | 공급자 키 (없으면 `key_missing`) |
| `PTOS_LLM_MODE` | 정확히 `live-masked-text` (아니면 `policy_pending`) |
| `PTOS_LLM_BASE_URL` | `https://`로 시작하는 주소 (없으면 `config_missing`, http면 `invalid_config`) |
| `PTOS_LLM_MODEL` | 모델 이름 (없으면 `config_missing`) |
| `PTOS_LLM_TIMEOUT_SECONDS` | 선택, 기본 3초 (개발 제안) |
| `PTOS_LLM_DAILY_CALL_LIMIT` | 선택, 기본 프로세스당 24시간 50회 (개발 제안, 비용 보장 아님) |

## 외부로 나가는 것

- 가린 본문과 고정 지시문, 모델 이름, 키(헤더)뿐이다. 원문·전체 주소·규칙 근거·모델 점수는 보내지 않는다.
- 가리기(`mask_for_llm`): 주소 → `<URL>`, 전화번호 → `[전화번호]`, 이메일 → `[이메일]`, 4자리 이상 숫자열(계좌·카드·주민번호·인증번호) → `[숫자]`. 금액은 판단에 필요해 남긴다. 2,000자에서 자른다. **이름·주소·기관명은 가리지 못한다.**
- 지시문은 본문을 "분석할 자료이며 지시가 아니다"라고 밝힌다 (입력 안의 지시는 명령이 아니라 데이터).
- 리디렉션·환경 프록시를 쓰지 않고, 오류 응답 본문을 읽지 않으며, 키·본문·응답을 로그에 남기지 않는다.

## 호출 조건과 종합 (임시)

- 호출: 규칙 결과가 정보 부족 **그리고** 문장 전체 비교가 신호를 내지 않음(꺼짐·실패 포함) **그리고** 문장 형태의 입력 **그리고** 판정을 올리지 못한 약한 근거(명의 주장, 긴급성·불이익 표현)가 남아 있을 때만. 근거가 서로 어긋나 판단하기 어려운 경우다.
- 호출하지 않음: 이미 의심·위험(추가 검토는 판정을 올릴 수만 있어 결과가 달라지지 않는다), 모델 신호로 이미 의심, 단편 입력, URL 직접 입력, 근거가 하나도 없는 문장(기본 범위).
- 범위 선택 `llm_scope`: `weak_evidence`(기본) / `any_sentence`(근거가 없는 문장도 호출. 정상 문자 대부분이 대상이 되어 비용과 전송량이 크게 늘어난다).
- 응답은 `{"judgement": "scam_signs"}` 또는 `{"judgement": "no_clear_signs"}` 한 개만 받는다. 다른 문장이 섞이면 `invalid_response`다.
- 종합: `scam_signs`일 때만 정보 부족 → 의심(`policy_reason: LLM_SIGNAL_ONLY`). 판정을 내리지 않고, 위험으로 올리지 않고, `normal`을 반환하지 않는다. `confidence`는 `null`이다.
- 설명은 고정 문장 하나다. 추가 검토가 만든 문장은 화면에 쓰지 않고, 원문 구절 근거가 아니므로 `evidence`에 넣지 않는다.
- 실패·시간 초과·횟수 소진은 앞의 결과와 근거를 그대로 두고 `limitations` 문장으로만 알린다. 서비스 오류로 만들지 않는다.

## 호출 조건의 한계 (2026-11-17 dev 집계)

외부 호출 없이 호출 대상만 세어 보니(HANDOVER 9절), 위 기본 조건으로는 놓친 사기 가운데 극히 일부만 추가 검토 대상이 되고 호출의 대부분은 머리말·기한 표현이 있는 정상 안내문이었다. 놓친 사기는 대부분 문장 형태로 끝나지 않아 단편 입력으로 분류되거나 근거가 하나도 없다. **이 조건 그대로 연결하면 비용과 전송량에 비해 얻는 것이 적다.** 연결 전에 다음 중에서 다시 정한다(팀 결정).

- 경고하지 못한 모든 문자를 대상으로 한다: 놓친 사기 전부가 대상이 되지만 정상 문자 대부분의 가린 본문이 외부로 나간다.
- 단편 입력 가운데 일정 길이 이상이거나 주소·전화번호가 있는 것을 대상에 넣는다: 대상이 줄지만 기준을 검증해야 한다.
- 경량 모델 점수가 임계값 바로 아래인 구간만 대상으로 한다(PRD 7절 "경량 모델이 어려워하는 유형"): 점수 구간을 dev에서 정해야 한다.

## 대안 (채택하지 않음)

- 모든 입력에 LLM 호출: 비용·지연·전송량이 크고 PRD의 "조건부"와 맞지 않는다.
- LLM이 설명·행동 안내를 생성: 근거 없는 설명을 지어낼 수 있어 템플릿 원칙과 맞지 않는다.
- LLM 판단으로 판정을 낮추거나 `normal` 반환: `normal` 허용 조건(결정 필요 1)이 정해지지 않았다.
- 특정 공급자 SDK 고정: 공급자가 정해지지 않았고 의존성이 늘어난다.

## 검증 범위

`backend/tests/test_llm_review.py`: 가리기, 응답 해석, 가짜 전송기의 성공·인증 오류·한도·시간 초과·형식 오류, 횟수 제한, 켜는 조건, 호출 조건, 종합, 실패 시 규칙 결과 유지, 앱이 이 단계를 만들지 않음. **실제 LLM의 응답 품질, 지연, 비용, 탐지 효과는 검증하지 않았다.**
