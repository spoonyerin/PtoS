# 규칙 기반 개발 버전의 임시 판정 정책 · rules-dev-v4

> **임시, 팀 확정 필요.** v3(T4, 2026-10-27)에서 추가한 신호와 규칙 A·B, v4 1차 보강(2026-11-09)의 관계 자기소개 위치 제한과 부정 범위 조정은 팀이 확정하지 않은 개발용 정책이다. 아래 "v3 신호 보강", "v4 1차 보강", "알려진 한계" 절을 본다.

PRD v1.2 FR-04~09와 개발설계서 5~7장의 **입력 충분성 → 근거 → 설명·행동** 원칙을 적용한다. 아래 내용은 이번 개발 증분의 검수 가능한 기준선이다. PRD가 확정한 판정 경계·정확도·신뢰도·점수 임계값이 아니다. 점수를 합산하거나 안전 확률을 만들지 않는다.

이 문서는 문자 규칙의 기준선이다. 후속 종합 정책은 [SAFE_BROWSING.md](SAFE_BROWSING.md)의 종합 판정(`RuleBasedAnalyzer`의 `analysis_version: rules-reputation-dev-v3`)과 [MODEL_POLICY.md](MODEL_POLICY.md)의 모델 종합(API 응답 `analysis_version: rules-model-dev-v2`)을 따른다. v4에서 두 값은 문자 규칙이 바뀌었음을 구분하려고 올렸으며 평판·모델 종합 방식은 바뀌지 않았다. 검증된 전체 해시 위협 일치만 URL 근거로 추가하며, 기존 문자 근거는 유지한다. 실제 외부 조회는 계속 보류 상태다.

## 현재 가능한 분석과 없는 분석

- 실행: 한국어 표현 패턴으로 실제 입력의 명의 주장, 금전·민감정보 요구, 링크 클릭·앱 설치 유도, 긴급성·불이익 압박을 찾는다. 문자열은 정규화하지 않으며 유연한 공백 패턴만 사용한다.
- 경량 모델: TF-IDF 기준선만 연결했고 규칙의 정보 부족을 의심으로 올릴 수만 있다([MODEL_POLICY.md](MODEL_POLICY.md)). 이 문서의 규칙 판정은 모델과 별개다.
- 미구현: URL 평판 조회. 유효한 URL이 있으면 기본 평판 단계는 `not_connected`, 없으면 `not_applicable`로 보고한다. 무효 후보는 평판 조회를 하지 않는다. URL 입력·추출 기준은 [URL_POLICY.md](URL_POLICY.md)에 분리했다. 조회를 수행한 것처럼 `benign`이나 `unknown`을 반환하지 않는다.
- 현재는 어떠한 입력에도 `normal`을 반환하지 않는다. 일상 안내·예방 교육에 위험 요구가 없더라도 미구현 분석 때문에 `insufficient_information`이다. 정상 안내문을 사기라고 단정하지도 않는다.
- `confidence`는 항상 `null`, `analysis_mode`는 `rules`, `is_demo`는 `false`다. 규칙의 경고도 실제 사기 확정이나 안전 보증이 아니다.

## 입력 충분성과 근거

- `action_identified`: 대상과 긍정적 요구 표현을 규칙이 함께 찾은 경우. 짧더라도 “인증번호를 알려주세요”는 구체적 요구이므로 경고할 수 있다.
- `sentence_present`: 문장 형태의 입력은 있지만 지원하는 요구가 확인되지 않은 경우. 이것은 전체 문맥을 이해했다는 의미가 아니다. 미구현 모델 때문에 판정을 보류한다.
- `url_only`: 직접 URL 입력은 형식만 확인하며 문장의 발신자·요구 행동이 없고 평판도 미연결이므로 정보 부족이다.
- `fragment`: 단어 나열·대상 불명의 짧은 구절 등. 글자 수 기준으로 충분성을 결정하지 않고 발신자·요구 행동이 드러나는 내용을 요청한다.
- 신호를 못 찾은 것, 입력이 단편적인 것, 모델·평판이 없는 것은 서로 다른 제한 사유로 전달한다. 알려진 위험 요구가 있으면 입력이 짧다는 이유로 그 근거를 지우지 않는다.

근거는 원문 그대로의 `snippet`, `start`, `end`, `factor_code`, `rule_id`, `source: rule`을 가진다. 좌표는 **원문 유니코드 코드포인트, 시작 포함·끝 제외**다. 프론트엔드는 구절을 일반 텍스트로 표시하며 JS의 UTF-16 인덱스로 원문을 잘라 강조하지 않는다. 명의 주장은 실제 기관 신원이나 사칭 사실을 검증한 것이 아니다. URL 포함/클릭 요구도 악성 URL이라는 뜻이 아니다. URL 경로·쿼리 안의 문자열은 문장의 요구나 명의 주장으로 해석하지 않는다.

## 부정·교육·인용 처리

- 대상 단어만으로 요구를 만들지 않는다. “인증번호를 요구하지 않습니다”, “송금하지 마세요”, “앱 설치가 필요 없습니다”는 긍정적 요구와 구분한다.
- 대상과 요구 사이에 부정·다른 행동이 끼면 연결하지 않는다. “인증번호를 알려주지 말고 점심시간을 알려주세요”를 인증번호 요구로 만들지 않는다.
- 사기 예시·주의 대상으로 명시한 인용 구절과 “알려주세요라는 문자는 피싱입니다” 같은 보고 표현은 실제 요구로 채택하지 않는다.
- “피싱 예방을 위해 인증번호를 보내주세요”처럼 보안/교육 단어와 **실제 요구가 함께 있는 문장**은 일괄 제외하지 않는다. 별도 문장의 예방 문구가 다른 문장의 요구를 상쇄하지 않는다.
- **(v4)** 명의·긴급·불이익 표현의 부정은 그 표현에 바로 이어지는 서술어(첫 연결 어미까지)에만 적용한다. “즉시 해지되니 무시하지 마세요”의 뒤 구절 부정은 앞의 불이익 예고를 지우지 않고, “정지되지 않습니다”, “중단되지 않으니 안심하세요”는 계속 부정으로 처리한다. 청구어 바로 뒤의 “없습니다/아닙니다”(“미납 금액이 없습니다”)는 청구가 없다는 안내로 보아 불이익 근거로 채택하지 않는다. 상세는 “v4 1차 보강” 절.
- 이 처리는 제한된 한국어 패턴이다. 모든 부정 범위·인용·대화 주체·우회 표현을 이해하지 못한다. 안내문/인용은 원문을 구분해 넣도록 안내하고 회귀 사례를 추가한다.

## 판정 순서 (점수 없이 명시한 조합)

1. 같은 결합 범위의 명의 주장 + 금전 요구 / 민감정보 요구 / 앱 설치 요구 → `dangerous` (`COMBINED_IDENTITY_REQUEST`). 이때 명의는 기존 명시적 명의 표현(“은행 담당자입니다”, “엄마 나 딸이야”)만이다. v3의 약한 명의 신호(대괄호 머리말, 가족 호칭)는 치지 않는다. **(v4)** “아들이야/딸인데/친구입니다” 같은 관계 자기소개는 구절 첫머리일 때만 명시적 명의로 본다.
2. 같은 결합 범위의 금전 요구 + 민감정보 요구 / 앱 설치 요구 → `dangerous` (`COMBINED_MONEY_REQUEST`).
3. 같은 결합 범위의 긴급성·불이익 압박 + 민감정보 요구 + 링크 클릭 요구 → `dangerous` (`COMBINED_URGENT_CREDENTIAL_LINK`).
4. **(임시, v3 규칙 A)** 같은 결합 범위의 명의(대괄호 머리말·가족 호칭 포함) + 불이익·청구 + 링크 요구 + 임박 기한 → `dangerous` (`COMBINED_NOTICE_PENALTY_DEADLINE`). 기한이 없거나 2일 이상 남았거나 날짜만 적혀 있으면 규칙 4에 해당하지 않고, 링크 요구가 있으므로 `suspicious`다.
5. **(임시, v3 규칙 B)** 같은 결합 범위의 가족 호칭 + 금전 요구 + 링크 요구 → `dangerous` (`COMBINED_FAMILY_MONEY_LINK`).
6. 위 조합 없이 긍정적 금전·민감정보·링크 클릭·앱 설치 요구가 있으면 → `suspicious`.
7. 그 외에는 → `insufficient_information`. 명의·긴급·불이익 표현이나 대괄호 머리말만 있으면 해당 표현은 보이되 단독으로 위험을 확정하지 않는다.

## v3 신호 보강 (임시, 팀 확정 필요)

T3 기준선에서 dangerous 라벨을 하나도 잡지 못한 원인(반말·의문형 가족 송금 요청, 대괄호 기관 머리말, “확인: 주소”형 링크 안내, 불이익·청구 대상어 부재)을 일반화한 말투 유형으로 보강했다. 특정 문장이 아니라 형태를 패턴으로 만들었고, 평가셋 문장을 규칙·테스트·문서에 넣지 않았다. 새 `FactorCode`를 만들지 않고 기존 코드 안에서 `rule_id`로 구분하므로 API 계약은 바뀌지 않았다.

| 신호 | factor_code / rule_id | 형태 |
| --- | --- | --- |
| 대괄호 기관 머리말 (약한 명의) | `IMPERSONATION` / `impersonation-header-v1` | 줄 첫머리 대괄호 묶음 안에 기관·업체·부서·공식 통지 유형 단어(은행, 카드, 공단, 법원, 택배, 통신, ~청/~부/~처, 센터, 보안, 통지, 채용 등)가 있는 경우. `[Web발신]`, `[광고]`, `[안내]`, `[알림]`, `[공지]`, `[예약안내]`처럼 업종이 없는 머리말과 문장 중간의 대괄호는 제외 |
| 가족 호칭 (약한 명의) | `IMPERSONATION` / `impersonation-family-v1` | 줄 첫머리에서 부모·조부모를 부르고 바로 1인칭(나/저)으로 말하거나 휴대폰 고장·분실을 설명하는 말투 |
| 반말·의문형 요청 | 기존 금전·민감정보 등 / 기존 `*-v1` | 줄래?, 줄 수 있어?, 주실 수 있나요?, 주면 안 돼?, 좀 부탁해, 대신 좀 해줄 수 있어? 등. “보내줄게” 같은 약속형은 제외. 상품권·기프트카드를 금전 대상에 추가 |
| “확인” 계열 링크 요구 | `LINK_CLICK` / `link_click-confirm-v1` | 링크·주소를 가리킨 뒤 “확인하세요/확인 바랍니다/조회해 주세요”, 또는 “확인: 주소”, “확인 바랍니다. 주소”처럼 확인 안내 바로 뒤에 URL이 오는 형태. 링크 대상이 없는 “확인 바랍니다”는 제외 |
| 링크 처리 안내 | `LINK_CLICK` / `link_click-guided-v1` | “해제하기: 주소”, “상세 내역 확인 및 납부: 주소”처럼 짧은 항목 이름 바로 뒤의 URL, 링크 뒤의 일반 처리 동사(“링크로 들어가 수정하세요”), “여기 링크 눌러서 …해 줘” 연결형. “여기·이곳”은 메시지에 URL이 있고 명시적 접속 동사가 있을 때만 링크로 본다. “주의·삭제·신고·자제하세요” 같은 회피 안내는 제외 |
| 불이익·청구 | `URGENCY_THREAT` / `urgency_threat-penalty-v1` | 청구어(미납, 연체, 체납, 과태료, 범칙금, 가산금, 압류, 법적 조치 등)는 단독으로, 상태 변화어(정지, 만료, 취소, 반송, 제한, 해지, 차단 등)는 “~될 예정”, “~됩니다”, “미확인 시 ~” 같은 예고·조건 형태일 때만. 과거형 완료 안내(“취소되었습니다”)와 부정형은 제외 |
| 임박 기한 | `URGENCY_THREAT` / `urgency_threat-deadline-v1` | 당일·금일·오늘·내일·익일 + 기한 표현(까지, 중, 안에, 이내, 자정, N시까지/부로/부터/예정), 자정까지, 24시간 이하의 N시간 이내, 1일 남음, D-1. 기한 표현이 없는 날짜어는 같은 구절에 불이익 예고가 있을 때만(“익일 서비스 해지 예정”) |

기존 긴급 패턴(`urgency_threat-v1`)은 그대로 두고 정책에서만 기한(지금 바로, 즉시 등)과 불이익(계좌·서비스 정지)으로 나눈다. 각 신호는 원문 코드포인트 좌표의 `snippet`과 같은 `rule_id`의 설명·행동 템플릿을 가진다. 머리말·가족 호칭 템플릿은 실제 발신자·가족 여부를 확인하지 않았다고 밝힌다.

결합 범위 보정: `확인:`, `상세내역:`처럼 라벨 뒤 줄 끝까지 URL만 있는 항목 이름과 “납부기한:” 같은 안내 항목 이름은 화자 라벨(`A:`)로 보지 않는다. “대신 좀 해 줘”의 대리 부사 “대신”은 대조 경계로 쓰지 않는다.

## v4 1차 보강 (임시, 팀 확정 필요, 2026-11-09)

v3의 알려진 불일치 두 가지를 고쳤다. 새 `FactorCode`를 만들지 않았고 API 계약은 바뀌지 않았다. 회귀 테스트(`backend/tests/test_rules_v4.py`)는 모두 직접 지은 문장이며 평가셋 문장을 규칙·테스트·문서에 넣지 않았다. 개발 중 평가는 `--split dev`만 실행했다(결과는 HANDOVER 9절).

| 변경 | 위치 | 내용 |
| --- | --- | --- |
| 관계 자기소개 위치 제한 | `IMPERSONATION` / 기존 `impersonation-v1` | “아들이야”, “딸인데”, “친구입니다”는 구절 첫머리일 때만 명시적 명의로 본다. 앞에는 대괄호 머리말, 인사(안녕·여보세요), 부모·조부모 호칭, 1인칭(나·저), 큰·작은·막내만 허용한다. “우리 딸이 친구인데…”, “부장님 아들입니다만…”처럼 문장 중간에서 제3자를 가리키는 표현은 명의 주장이 아니다. 빈 줄 뒤 직접 요구로의 제한된 문단 연결은 그대로다 |
| 부정 범위 | 명의·긴급·불이익 표현 | 부정(지 마/지 않/아니/필요 없 등)은 표현 뒤 첫 연결 어미(되니, 되며, 으니, 면, 지만, 는데, 어서·해서·셔서, 고 등)까지만 본다. “라고·라며”의 인용 연결은 범위 끝으로 보지 않는다. “확인하지 않으면”, “납부하지 않을 경우” 같은 조건형 부정은 앞 표현을 부정하지 않는다. 표현이 연결 어미로 끝나면(“택배 기사인데요”) 뒤 구절 부정의 영향을 받지 않는다. 요구 동사(금전·민감정보·링크·앱)의 부정 판단은 바꾸지 않았다 |
| 청구 부재 안내 | `URGENCY_THREAT` / `urgency_threat-penalty-v1` | 청구어(미납, 연체, 체납, 과태료 등) 뒤 20자 안의 첫 서술어가 “없다·아니다” 계열이면(“미납 금액이 없습니다”, “연체 내역이 없고”) 불이익 근거로 채택하지 않는다. “미납 요금이 있습니다”는 유지한다. 부정 범위 조정으로 이 문장들이 새로 불이익 근거가 되어 머리말·링크·임박 기한과 함께 규칙 A로 이어지는 경로를 막는다 |
| 조건 ‘시’ 오인 | `URGENCY_THREAT` / `urgency_threat-penalty-v1` | “미확인 시 해지”의 조건 ‘시’ 패턴이 “즉시·동시·수시·상시”의 ‘시’를 잡아 “즉시” 근거와 겹쳐 불이익 근거가 사라지던 문제를 고쳤다 |

검토 후 채택하지 않은 후보:

- **업종 없는 머리말·“고객님,” 호칭(미채택).** `[안내]`·`[공지]`·`[알림]`과 줄 첫머리 “고객님,”을 가장 약한 명의 신호로 두고 규칙 A에서만 세는 방식을 실험했다. dev에서는 normal 위험 0건 유지, 판정이 낮아진 위험 행 0건이었지만, 직접 지은 정상 택배 안내(“[안내] … 오늘 반송 예정 … 배송 조회: 주소”)가 규칙 A로 `dangerous`가 되어 코드를 되돌렸다.
- **링크 표시형 안내(“배송조회: 주소”) 단독을 정보 부족으로 낮추기(이번 범위 제외).** 링크만 보여 주는 실제 스미싱의 경고가 약해진다.
- **스킴 없는 주소, 날짜만 적힌 기한(이번 범위 제외).** 오탐 위험이 크다. 아래 한계 절을 본다.
- **답장 유도·전화·콜백, 과도한 혜택·당첨, 비밀유지 요구(2차 묶음, 보류).** 새 `FactorCode`가 필요한 계약 변경이라 별도 승인 후 진행한다.

### 알려진 한계 (v4 기준)

- **답장 유도 신호가 없다.** 가족 호칭 + 금전 요구에 “이 번호로 답장 줘”만 있으면 규칙 B가 성립하지 않아 `suspicious`다. 답장 유도를 신호로 만들려면 새 `FactorCode`(계약 변경)가 필요해 2차 묶음으로 보류했다.
- 날짜만 적힌 기한(예: “10/28까지”, “08/16일자”)은 받은 시점을 알 수 없어 해석하지 않는다(v4에서도 제외: 받은 시점을 모르는 상태에서 임박으로 해석하면 오탐 위험이 크다). “기한 내”, “납기 경과”처럼 값이 없는 기한, 날짜어 없이 시각만 있는 기한(“15시까지”)도 임박 기한이 아니다. 이런 위험 메시지는 규칙 A가 아니라 `suspicious`로 남는다.
- **업종 없는 머리말은 정상 안내 오탐 위험 때문에 명의로 보지 않는다.** `[안내]`, `[공지]`, `[알림]`처럼 업종이 없는 머리말이나 머리말 없는 “고객님, …” 형태는 명의가 없어 규칙 A가 성립하지 않는다. 후보 대안: 업종 없는 머리말을 규칙 A에서 청구어형 불이익(미납·연체·과태료 등)과 함께일 때만 세는 방식. 상태 변화형 불이익(반송·정지 등)과는 묶지 않는다. 정상 안내가 충분한 새 평가셋에서 측정한 뒤 검토한다.
- 스킴 없는 주소(`example.com/...`)는 URL 정책상 추출하지 않으므로 그 앞의 항목 이름도 링크 요구가 되지 않는다(v4에서도 제외: 파일명·버전·이메일 등 오탐 위험이 크고, 추출하면 평판 조회로 외부 전송 범위가 넓어져 별도 합의가 필요하다).
- 정상 안내의 “배송조회: 주소”, “예약 확인: 주소”도 링크 요구로 잡혀 `suspicious`가 된다(v4에서도 제외: 낮추면 실제 스미싱의 경고가 약해진다. 공식 도메인 대조를 도입할 때 다시 검토한다). 머리말·불이익·임박 기한이 함께 있는 정상 안내(예: 택배사 머리말 + 당일 미수령 시 반송 예정 + 조회 링크)는 규칙 A에 걸릴 수 있다.
- **(v4) 관계 자기소개의 위치 제한.** 이름 등 허용되지 않은 말이 앞에 오는 관계 자기소개(예: “저는 OO 친구인데요”)는 강한 명의로 잡지 않아 금전 요구가 `suspicious`에 머물 수 있다.
- **(v4) “없다”형 부정의 범위.** 청구어 바로 뒤의 “없다·아니다”만 처리한다. “필요는 없습니다”처럼 다른 위치의 “없다”는 부정으로 인식하지 않으며, 청구어 뒤 20자 안의 첫 서술어만 보므로 긴 수식이 끼면 놓칠 수 있다. 부정 범위는 제한된 연결 어미 목록으로만 끊으므로 표시 없는 긴 수식 구조는 이해하지 못한다.
- 고정 평가셋 결과: v3은 dev에서 개발하고 test는 마지막에 한 번만 비교했다. v4는 dev만 실행했고 test는 실행하지 않았다. 기존 test는 같은 1인 라벨링·합성 중심이며 이미 여러 번 본 분할이라 독립 검증이 아니다. 최종 비교는 새로 봉인한 test로 한다. 수치는 HANDOVER 9절을 본다.

## 문단과 결합 범위 · v2 변경

v1은 빈 줄마다 모든 신호 결합을 끊었다. OCR이 `은행 담당자입니다.` 다음에 빈 줄을 넣으면 같은 요구의 판정이 달라지는 문제가 있었다. v2는 원문/줄바꿈을 수정하지 않고 **신호의 결합 범위**만 계산한다. `text`와 사용자 확인을 거친 `ocr_text`에 같은 규칙을 적용한다.

- 기본은 빈 줄 경계다. LF·CRLF와 공백이 있는 빈 줄을 동일하게 취급한다.
- 예외는 **명의 주장만 있는 도입 문단 → 바로 다음 문단의 직접적인 금전·민감정보·앱 설치 요구**다. 도입에 휴무 안내 등 다른 내용이 있거나 중간 문단이 있으면 연결하지 않는다. 다음 문단의 첫 요구 앞에는 공백/지원하는 긴급 표현만 허용한다. URL 내부 문자열은 이 검사에서도 제외한다.
- 두 문단 중 하나라도 화자/메시지 표시, 인용 부호, 교육/주의 문맥 단어가 있으면 이 예외를 적용하지 않는다. 다음 문단에 다른 명의 주장이 있는 경우도 예외 연결하지 않는다. 일반적인 금전 요구 문단과 인증번호 요구 문단 등은 무조건 합치지 않는다.
- `A:`, `사용자:`, `[발신자] [시각]` 등 명시된 라벨, `>` 인용 표시, `--`/`==` 계열 구분선은 빈 줄이 없어도 결합 경계다. 따옴표로 둘러싸인 구절의 안/밖도 분리한다. 단독으로 인용된 한 메시지 안의 실제 위험 조합은 유지하고, 교육용으로 명시된 인용은 기존 제외 규칙을 유지한다.
- 문단 연결 시 `input_assessment.reasons`에 제한된 연속 문맥 규칙을 적용했다고 표시한다. 근거 구절·좌표는 여전히 수정하지 않은 원문의 코드포인트다. OCR 줄바꿈을 지우거나 누락 글자/URL을 복원하지 않는다.

| 입력 형태 | 현재 결과 |
| --- | --- |
| `은행 담당자입니다.` + 빈 줄 + `인증번호를 알려주세요.` | 위험: 제한된 도입·요구 연결 |
| `은행입니다. 휴무 안내입니다.` + 빈 줄 + 인증번호 요구 | 의심: 일반 문단을 합치지 않음 |
| `A: 은행입니다.` + `B: 인증번호를 알려주세요.` | 의심: 다른 라벨의 신호를 합치지 않음 |
| `“은행입니다. 인증번호를 알려주세요.”는 사기 예시입니다.` | 정보 부족: 교육 인용 제외 |

이 방식도 실제 대화 주체를 이해하는 모델은 아니다. **표시 없는 화자 전환과 모든 메신저 헤더·교육/인용 표현을 판별할 수 없다.** 관련 문맥을 확인할 수 없으면 사용자는 하나의 발신 메시지만 구분해서 입력해야 한다. 숫자 점수/확정 임계값을 추가하지 않았으며 위 조합은 범죄·악성 여부 검증이 아닌 **개발용 경고 정책**이다.

## 설명과 행동

각 신호는 같은 코드의 검수용 템플릿과 연결한다. 링크가 없고 클릭 요구도 없으면 링크를 발견했다고 쓰지 않는다. 인증번호·금전·앱 설치 요구가 없으면 해당 요구를 발견했다고 쓰지 않는다. 명의 주장에는 실제 신원 미확인 안내를 붙인다. 동일한 행동은 중복 제거한다. 기본 확인 안내는 직접 확인한 공식 홈페이지/연락처를 이용하도록 하며 연락처나 기관 사실을 만들어내지 않는다.

## 다음 분석기 연결 경계

`Analyzer.analyze(AnalysisInput) -> AnalysisResult`를 유지한다. `RuleBasedAnalyzer`는 신호 추출, 임시 정책, 설명 템플릿을 분리한다. `analysis_stages`가 각 단계의 수행 상태를 보고한다. 향후 복합 Analyzer에서 규칙 결과와 실제 모델/평판 결과를 수집한 뒤 검증된 별도 정책으로 종합한다. 미구현 단계의 성공을 가정하거나 규칙 부재를 정상 근거로 승격하지 않는다. 공급자 장애는 단계 제한 또는 서비스 오류로 분리한다.

API의 `demo_scenario`는 제거한다. 오래된 클라이언트가 이 필드를 보내면 422다. 고정 예시 분석기는 이번 버전에서 제거하며 별도 데모 엔드포인트도 두지 않는다. 결과 열거형의 네 값은 향후 호환성을 위해 유지한다.

## 필수 회귀 검증

일상 안내문, 명의만 있는 안내, 부정 표현(v4: 뒤 구절 부정·조건형 부정·청구 부재 안내 포함), 관계 자기소개의 위치(v4), 예방 교육·인용, 교육 문구와 실제 요구의 혼합, 결합 요구, 단일 요구, 단어 나열, 짧은 구체적 요구, URL만 있는 입력, 제한된 문단 연결과 연결하면 안 되는 문단/화자, LF/CRLF·이모지가 있는 근거 좌표를 확인한다. 이 테스트는 규칙의 회귀 검증이며 탐지 성능/최종 MVP 인수 검증이 아니다. 실제 AI·외부 URL 조회·디자인 개편은 이번 정책 수정에 포함하지 않는다.
